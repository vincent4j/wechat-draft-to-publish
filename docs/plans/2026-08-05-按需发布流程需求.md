# 按需发布流程需求

## 需求概述

优化 `wechat-draft-to-publish` 的用户交互。用户不应先理解六个内部步骤和编号，而应直接说明想得到哪些公众号产物。工作流负责把自然语言要求换算成执行清单，支持只做一项、执行连续区间、选择多个产物或生成完整发布包。

保留现有六项处理能力、子 Skill 配置继承、产物校验和安全清理机制，不改变各子 Skill 的实现。

## 功能结构

### 执行范围

- “全部处理”“完整发布稿”：执行完整六步。
- “只做封面”“只排版”：只执行对应步骤，完成后停止。
- “从配图做到排版”：执行连续范围。
- “正文别动，只做配图、封面和排版”：执行指定步骤并明确跳过其他步骤。
- 多个不连续产物：只执行用户点名的步骤，不自动补齐中间步骤。

### 执行方式

- **直接完成**：按确定范围连续执行，每一步反馈进度但不暂停。
- **边做边看**：在正文、配图、封面和排版的实际结果完成后暂停；摘要、朋友圈文案和机械校验连续完成。
- 兼容旧入口：`自动 N`、`分步 N` 和单独数字继续有效。

### 结束回执

无论只做一项还是完整处理，结束时必须告诉用户：

- 实际完成了什么；
- 明确跳过了什么；
- 生成或修改了哪些文件；
- 执行了哪些检查；
- 是否清理以及清理结果；
- 哪些范围外后续产物可能已经过期。

## 数据来源

- 用户指定的 Markdown 草稿或已有阶段稿。
- 用户自然语言中的目标产物、排除项和执行方式。
- `references/defaults.md` 的当次默认参数。
- 子 Skill 生成的正文、图片、封面和排版产物。

## 技术要求

- 当前用户要求优先于工作流默认参数，工作流默认参数优先于子 Skill 偏好。
- 用户明确指定产物时不再要求选择步骤编号或模式。
- 执行清单不得自动扩大到未请求步骤。
- 边做边看确认实际结果，不增加配图或封面的生成前方案确认。
- 只做局部流程时默认不执行收尾清理。
- 只有第 4、5、6 步均在本次范围内并通过校验，或用户明确要求时，才执行清理。
- 保持摘要 120 字以内、朋友圈文案 100 个汉字以内等既有校验合同。

## 设计要求

- 入口使用用户结果语言，不要求用户理解内部步骤。
- 范围和方式都不清楚时，才展示“直接完成 / 边做边看”菜单。
- 每一步回执简洁说明实际产物、检查和处理依据。
- 完整回执必须区分实际完成、明确跳过和未完成，不能把计划写成结果。
- 用户确认前只能说发布稿已生成，不能说已经发布。

## 验证标准

- “只做封面”只识别封面，不改正文、不生成其他产物、不清理。
- “正文不改，从配图做到排版，边做边看”只执行第 2—4 步，并在实际结果后暂停。
- 笼统要求“处理成公众号文章”时展示双模式菜单，不擅自执行。
- 单项任务结束后仍有完整执行回执。
- 发布包一致性检查以最终使用的 Markdown 正文为权威来源。
- 工作流契约校验、Python 编译、YAML 解析和 diff 格式检查通过。
