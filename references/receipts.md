# 对话与回执

## 开始话术

> 已识别文章草稿。本工作流包含：
>
> 1. **去除 AI 味**：让文章表达更自然
> 2. **正文配图**：生成配图并插入文章
> 3. **封面制作**：生成公众号封面
> 4. **文章排版**：生成可复制到公众号的排版稿
>
> 请选择从哪一步开始，直接回复序号。

不要在下面追加各序号的解释。

## 成功回执

每一步完成后使用以下结构：

```markdown
第 N 步「步骤名称」已完成。

**做了什么**

- 只列本步骤实际完成的操作。

**为什么这样做**

用简洁文字解释关键处理依据，不复述操作列表。

**生成或修改的文件**

- 列出可供用户检查的文件。

**检查结果**

- 列出本步骤实际执行的检查及结果。

**建议你重点检查**

- 列出需要用户主观判断的内容。

**下一步：第 N+1 步「下一步名称」**

用一句话说明下一步会做什么。

- 回复 `N+1`：确认进入下一步
- 如需修改当前结果，直接告诉我修改要求
```

回执必须同时回答“做了什么”和“为什么这么做”。不要只说“已完成”。

## 修改后的回执

用户要求重做当前步骤时，完成后说明：

- 修改了什么
- 为什么这样调整
- 哪些文件被替换
- 检查结果

然后再次等待用户确认，不自动进入下一步。

## 最终回执

第 4 步完成后不再显示下一步：

```markdown
第 4 步「文章排版」已完成。

**做了什么**

- 列出生成的排版产物和图片处理方式。

**为什么这样做**

说明字号、留白、目录和图片复制方案的依据。

**生成或修改的文件**

- 列出纯净 HTML 和一键复制预览版。

**检查结果**

- 目录与标题数量
- 图片引用与内嵌状态
- 排版校验结果

**请你进行最后确认**

打开一键复制预览版，将内容复制到微信公众号编辑器，检查图片、字号和段落间距。

- 回复 `完成`：确认本次工作流结束
- 发现问题：直接描述问题
```

用户确认前，只能说“已生成发布稿”，不能说“已经发布”。

## 失败回执

某一步失败时也要给回执：

```markdown
第 N 步「步骤名称」未完成。

**已经完成**

- 列出成功部分。

**未完成**

- 列出失败部分。

**原因**

说明可验证的失败原因，不猜测。

**保留的文件**

- 列出仍可使用的产物。

修复或补充条件后，等待用户确认是否重试本步骤。
```
