# 对话与回执

## 双模式开始话术

> 已识别文章草稿。本工作流包含：
>
> 1. **去除 AI 味**：让文章表达更自然
> 2. **正文配图**：生成配图并插入文章
> 3. **封面制作**：生成公众号封面
> 4. **文章排版**：生成可复制到公众号的排版稿
> 5. **公众号摘要**：生成 120 字以内的后台摘要
> 6. **朋友圈转发文案**：生成 100 个汉字以内的朋友圈配文
>
> 如果要生成完整发布包，请选择执行方式：
>
> - **直接完成**：按默认方案连续处理，中间反馈进度但不暂停
> - **边做边看**：在正文、配图、封面和排版这些关键结果完成后确认
>
> 也可以直接说“只排版”“只做封面”“从配图做到排版”或列出你需要的产物。

不要在下面追加其它解释。只有范围和执行方式都不明确时才使用这段话术；用户已经明确要
完整处理、只做某项或指定范围时，不再展示菜单。`自动 N`、`分步 N` 和单独数字按兼容
规则处理。

## 执行摘要

两种模式开始执行前都使用；第一句根据模式写“已进入直接完成”或“已进入边做边看”：

```markdown
已进入「直接完成 / 边做边看」。

**本次执行**

- 输入文件：列出文章路径
- 实际执行：只列本次会执行的步骤和目标产物
- 明确跳过：列出未纳入范围的步骤；完整处理时写“无”
- 默认参数：只概括本次实际会用到的配图、封面、排版或文案参数
- 预计产物：只列本次会生成或修改的正式文件
- 收尾处理：说明本次是否满足清理条件；不满足时写“不执行清理”

现在开始执行。
```

发出执行摘要后立即开始，不得要求用户再回复 `开始`。不得把未纳入执行范围的产物列入
“预计产物”。边做边看是在关键结果生成后暂停，不是在摘要后等待开始。

## 成功回执

每一步完成后使用以下结构：

```markdown
第 N 步「步骤名称」已完成。

**做了什么**

- 只列本步骤实际完成的操作。

**为什么这样做**

用简洁文字解释关键处理依据，不复述操作列表。

**生成或修改的文件**

- 列出可供用户检查的文件。

**检查结果**

- 列出本步骤实际执行的检查及结果。

**建议你重点检查**

- 列出需要用户主观判断的内容。

**接下来**

边做边看且本步骤属于第 1 至第 4 步时，用一句话说明执行清单中的下一项：

- 回复 `继续`：进入执行清单中的下一项
- 如需修改当前结果，直接告诉我修改要求
```

回执必须同时回答“做了什么”和“为什么这么做”。不要只说“已完成”。当前步骤已经是
执行范围末尾时不显示“接下来”，改用完整执行回执。第 5、6 步不设置单独确认门。

## 直接完成进度回执

直接完成每一步完成后作为进度消息发送，不暂停：

```markdown
第 N 步「步骤名称」已完成。

- 产物：列出本步骤主要文件
- 检查：列出关键检查结果
- 处理依据：一句话说明关键选择

继续执行：第 M 步「执行清单中的下一项」。
```

M 不要求等于 N+1，因为执行清单可以跳过步骤。当前步骤已经是执行范围末尾时改用完整
执行回执。进度回执不得要求用户回复序号。

## 修改后的回执

用户要求重做当前步骤时，完成后说明：

- 修改了什么
- 为什么这样调整
- 哪些文件被替换
- 检查结果

边做边看时再次等待用户确认；直接完成收到修改要求后停止自动推进，完成修改并说明影响，
等待用户决定是否恢复执行清单。

## 完整执行回执

到达本次执行范围末尾后使用，无论执行了一步还是完整六步：

```markdown
本次公众号文章处理已完成。

**实际完成**

- 按执行顺序列出真正完成的操作及关键处理依据。

**明确跳过**

- 列出未纳入本次范围的步骤；完整六步均完成时写“无”。

**生成或修改的文件**

- 只列实际生成或修改成功的文件。

**检查结果**

- 列出本次实际执行的内容、图片、排版、摘要、朋友圈文案和发布包一致性检查。
- 未执行的检查不要写成通过。

**收尾处理**

- 列出实际删除数量、保留的正式资源和未识别但保留的文件；未满足清理条件时明确写“未执行清理”及原因。

**需要留意**

- 列出因较早产物更新而可能已经过期、但不在本次范围内所以没有重做的后续产物；没有则写“无”。

**接下来怎么用**

根据本次实际产物说明使用方法。例如生成排版预览时提示打开并复制；生成摘要或朋友圈文案时说明对应粘贴位置。不要介绍本次没有生成的文件。

- 回复 `完成`：确认本次工作流结束
- 发现问题：直接描述问题
```

完整回执必须回答用户关心的“你都做了什么”，并区分实际完成、明确跳过和未完成。用户确认
前只能说“已生成发布稿”或“本次处理已完成”，不能说“已经发布”。

## 失败回执

某一步失败时也要给回执：

```markdown
第 N 步「步骤名称」未完成。

**已经完成**

- 列出成功部分。

**未完成**

- 列出失败部分。

**原因**

说明可验证的失败原因，不猜测。

**保留的文件**

- 列出仍可使用的产物。

修复或补充条件后，等待用户确认是否重试本步骤。
```
